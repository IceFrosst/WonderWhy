# WonderWhy: interactive playback and hardware test

This was the original playback proposal. Use the [current design handoff](Design_Handoff.md) for the live Three.js viewer, 72-angle fallback, updated controls, and measured hardware results.

Start with **one kettle**. The Android app takes one photo from the wearer’s point of view and identifies the object. The glasses Web App plays the existing Explore explanation; **Inspect** opens a pre-rendered turntable of the same object. Make the reveal useful: rotate around the jug, separate the parts, move the heating coil into the centre, then zoom in and hear why steam switches the kettle off.

## What is possible

| Path | What the wearer can do | Evidence and limits |
| --- | --- | --- |
| **Glasses Web App + pre-rendered atlas** | Rotate by selecting an angle; pan and zoom the picture; switch between assembled and exploded views. | [Local kettle proof](app/turntable/index.html): two WebP sheets, each with 36 real renders at 10° intervals. Instant frame selection after load, no video seeking. Pan and zoom are image transforms. A second pitch row could add a look from above; arbitrary pitch needs more renders or a live model. The standalone proof and the hosted kettle film share these images. Rotation has been verified in Chromium. The band controls still need a real hardware check. |
| **Glasses Web App + MP4** | Scrub a dedicated turntable with one known angle per frame; play/pause the separate explanation clips. | Existing `ExploreView` already layers labels over muted MP4s. Those clips move the camera and animate other things at the same time; don't map an arbitrary clip's timestamp to an angle. A dedicated MP4 can use short keyframe spacing, but repeated seeks still need to be tested on glasses. |
| **Glasses Web App + live model** | Free orbit, pitch, zoom and pan; update part labels and cross sections as the object moves. | A possible next step with a small model and a measured frame budget. The repo's Three.js renderer currently runs offline to make media; porting its rich rendering to the glasses is unnecessary for the demo. |
| **Android Device Access Toolkit only** | Pinch to capture and step through cards. Add several pre-rendered angle/zoom cards or a “Watch animation” action. | Meta supports a URL MP4 as the whole display view. The installed Android SDK player has `play()` and `close()`, with no public seek or pause method. Treat the clip as a short narrated segment and restore the card on finish, error or Back. Use the still cards for reliable stepped manipulation. |

Meta documents [opt-in pinch-and-drag](https://developers.meta.com/wearables/web-apps/) and [Pointer Events, D-pad and pinch input](https://github.com/meta/meta-wearables-webapp/blob/main/plugins/meta-wearables-webapp/skills/ai-glasses-webapp-device/SKILL.md). Start with Rotate / Zoom / Pan modes (one gesture, one meaning at a time) and discrete controls as a fallback. In Explore, keep pinch-to-step separate from the optional Inspect mode. Inside Inspect, pause the lesson and keep Reset and Back easy to find. The proof uses browser drag and buttons; the integrated screen maps the glasses D-pad and Select to the same controls. Keep the atlases off the home screen's initial load and load the exploded view while the lesson is playing. For evidence, record the hand and display together or cut on the same real gesture. Describe it as “live Neural Band control over pre-rendered views.”

## Narration

Record the hero lines once with a human voice or a consistent licensed voice. Keep a short cue per beat; say what changed and why. Start it when its highlight appears, stop it as soon as the wearer changes beat, and provide Listen/Replay, Mute and a caption. Use the repo's caption and anchor tracks to sync the guided lesson; keep narration separate from the interactive view so seeking through angles never scrubs the audio. For ad hoc follow-ups, speak the checked answer when available and keep the text visible. Do not open the question microphone while the app is speaking. The proof's Listen button uses the browser's speech voice as a placeholder; the APK's on-device transcription is for questions and does not narrate the explanation.

> “See the coil below the jug? It heats the water. When steam reaches the switch, a metal disc bends and cuts the power.”

On hardware, verify the sound comes from the glasses, the first sentence is intelligible in a noisy room, and a question asked after narration makes it to the app. The submission edit may use the same narration as a separate track. Mark simulator footage and edits for time where relevant.

## Phone handoff when the glasses arrive

1. Get **Meta Ray-Ban Display** and the **Meta Neural Band**. The team’s [Pixel 8 was already configured](team-notes/Test_Now.md). For another phone use **Android 12+** for our APK (our repo has no iPhone build). Update and sign into Meta AI, turn on Bluetooth, use a reliable Wi-Fi connection, and [pair the glasses in Meta AI](https://www.meta.com/en-gb/help/ai-glasses/852077233025627/) and [pair the band](https://www.meta.com/en-gb/help/ai-glasses/770840295349358/). Let firmware updates finish and check the band can navigate the stock home screen. If the loaner is still tied to someone else's account, have the booth handle the handoff.
2. Turn on Meta AI Developer Mode. Install the repo's `app/android/app/build/outputs/apk/debug/app-debug.apk` (**Physics Lens**, even though the pitch name is WonderWhy). Use a USB data cable and `adb install -r` with USB debugging, or have the team pass you the APK for local installation. In the app open **Developer**, turn **Mock glasses** and **Demo data** off, restart, tap **Connect glasses**, approve the Meta AI registration callback, and allow Bluetooth/camera; allow mic for spoken questions. Enter the team's HTTPS bridge and token separately in Developer settings. A LAN or USB bridge is fine for native testing; the glasses Web App needs the team's HTTPS endpoint too. Verify it from the test phone before checkout.
3. In Meta AI add the **Physics Lens Web App** to the glasses (scan the [install QR](app/deploy/install-qr.png) with the phone, or follow [Meta's manual installation route](https://github.com/meta/meta-wearables-webapp#4-deploy-to-glasses)). Use the team’s current private install link if the app needs a bridge token. The checked-in QR doesn't carry a secret. For only the Web App with a library demo object, the APK is optional.
4. **Test in this order:** (a) Camera-only **off**: pinch at the kettle → good card → spoken or typed follow-up. Record three real wait times. (b) **Within 120 seconds**, close the native display experience and open the Web App: look for the same result from the bridge replay. (c) Turn on **Film on glasses (Web App)** and reconnect, then Web App → **Take photo**; see whether it stays in front through capture and receives the right object. This route already exists, but its real-glasses coexistence is unverified in the repo; the native prompt for a spoken question is skipped in this mode. If it fails, demo native capture and Web App inspect as successive steps, or use native cards and separately show the Web App with a library object.
5. Kettle film → Down → Right to Inspect → pinch. Then test drag, D-pad steps and Back on the glasses. Try **Record display** from Meta AI or glasses settings ([Meta FAQ](https://developers.meta.com/wearables/faq/)); run a short capture first to check the display and audio you actually get. Save one successful take and a truthful fallback recording. Record the Meta AI and firmware versions beside the results.

The repo has notes from a real Band pinch and a real spoken question on November 14, despite earlier docs saying hardware hadn't been used. End-to-end capture while the Web App is open, the new Inspect controls, and narrated output all still need evidence. [Meta's session guide](https://github.com/meta/meta-wearables-dat-android/blob/main/AGENTS.md) says a competing experience may pause or stop the native session. [Meta's Android video example](https://github.com/meta/meta-wearables-dat-android/blob/main/.cursor/rules/display-access.mdc#send-video) shows video as the root, separate from card UI.
